# T-11d — Themes: elf Paletten, Leisten-Token, feste Marke — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Die acht gewachsenen Paletten durch die **elf** aus `ux-standards/references/themes.md` ersetzen, die fehlenden Token nachziehen (Flächen, Text, Ränder, Akzent-Kontrast, Leisten), Status-Farben themeunabhängig in heller/dunkler Stufe führen und den Marken-Verlauf vom Theme lösen.

**Architecture:** `base.scss` bleibt der einzige Ort der Paletten; jedes Theme trägt seinen vollständigen Token-Satz im eigenen `[data-theme]`-Block (Grund siehe Constraints). Die `--c-*`-Rückwärts-Aliase aus T-11b werden **abgeschafft** — nach T-11b liest sie nur noch `ThemesPanel`, und die wird hier ohnehin angefasst. `useTheme` bekommt die neue Liste und folgt ohne gespeicherte Wahl der Systemeinstellung.

**Tech Stack:** SCSS (`base.scss`, `_variables.scss`), Vue 3 SFC, Vitest.

## Global Constraints

- **Werte wörtlich aus `~/.claude/skills/ux-standards/references/themes.md`.** Nichts runden, nichts „harmonisieren" — gleicher Name heißt gleiche Farbe über alle Apps. Wer eine Zahl anpasst, bricht genau die Zusage, deretwegen das Dokument existiert.
- **Alles Theme-Abhängige gehört in den `[data-theme]`-Block**, nie auf `:root` mit `var()`-Verweis. Ein Custom Property mit `var()` wird dort ersetzt, wo es deklariert ist, und vererbt sich fertig aufgelöst — die Theme-Vorschau in `ThemesPanel` (jede Kachel trägt ihr eigenes `data-theme`) zeigte sonst 11× dasselbe Theme. In T-11b bereits einmal beinahe passiert.
- **Vom Auftraggeber entschieden (2026-08-15):**
  - **nur die elf Skill-Themes** — `earth`, `night`, `sunset`, `neon` entfallen ersatzlos;
  - **keine Umschreibung** gespeicherter Wahl: wer `classic` gespeichert hat, bekommt künftig das neutralgraue `classic`, nicht das pflaumenfarbene (das heißt jetzt `mangolila`).
  Wer eines der vier entfallenen Themes gespeichert hat, muss **sauber** auf die Vorgabe fallen (kein leeres `data-theme`, keine ungestylte Seite).
- **Marke ist themeunabhängig:** `--brand-from: 223 84 48` (`#df5430`), `--brand-to: 129 44 124` (`#812c7c`), `--brand-contrast: 255 255 255`, Verlauf **135°**. Ersetzt das bisherige `--c-grad` (pro Theme verschieden, 120°).
- **`--brand-contrast` ≠ `--accent-contrast`.** Ersteres ist fest weiß (Zeichen auf dem Marken-Verlauf), Letzteres wechselt mit dem Theme und ist in sechs der elf Paletten nahezu schwarz. Verwechslung lässt das Zeichen in genau diesen sechs verschwinden.
- Kontrast wird **geprüft, nicht geschätzt** — Grenzwerte in der Verifikation unten.
- Scoped SCSS; Farben nur über Token. Gate je Task: `npm run build` sauber **und** `npm test` grün.
- Arbeitsverzeichnis: `dashboard/`.

```scss
// ─── Theme-Paletten (11 Themes, persistent via data-theme) ────────────────────
// Werte 1:1 aus ux-standards/references/themes.md — gleicher Name, gleiche Farbe
// über alle Apps. Jedes Theme trägt seinen vollen Token-Satz im eigenen Block:
// ein Custom Property mit var() würde schon auf :root aufgelöst und die
// Theme-Vorschau (Kachel mit eigenem data-theme) zeigte 11× dasselbe Theme.
:root,
[data-theme='mangolila'] {
  --surface-page: 20 16 26;      --surface-card: 30 24 39;
  --surface-raised: 42 33 54;    --surface-sunken: 14 11 19;
  --text-primary: 244 241 249;   --text-secondary: 165 155 184;
  --text-muted: 118 109 136;
  --border-default: 52 42 66;    --border-subtle: 38 31 49;
  --accent: 232 112 58;          --accent-contrast: 20 16 26;
}
```

`mangolila` teilt sich die Regel mit `:root` (es ist die Vorgabe für dunkel).

Themes **mit** Leisten-Token laut Skill: `slate`, `aurora`, `carbon`, `sepia`, `meadow`. Nur die dort genannten setzen, die übrigen erben den Rückfall (siehe Step 4).

- [ ] **Step 3: Status-Farben in zwei Stufen**

Auf `:root` die **helle** Stufe (gilt für `paper`, `sepia`, `meadow`, `mono`):

```scss
// ─── Bedeutungstragende Farben (themeunabhängig, zwei Stufen) ─────────────────
:root {
  --status-ok: 22 133 94;
  --status-near: 180 83 9;
  --status-out: 198 47 47;
}
```

Die **dunkle** Stufe in den sechs dunklen Themes (`mangolila`, `classic`, `slate`, `ocean`, `forest`, `aurora`) — als eine gemeinsame Regel, damit die Werte einmal stehen:

```scss
[data-theme='mangolila'], [data-theme='classic'], [data-theme='slate'],
[data-theme='ocean'], [data-theme='forest'], [data-theme='aurora'],
:root {
  --status-ok: 25 158 112;
  --status-near: 217 119 6;
  --status-out: 224 82 82;
}
```

**Achtung Reihenfolge:** `:root` erscheint in beiden Gruppen. Die dunkle Stufe muss **nach** der hellen stehen, damit die Vorgabe (dunkel = mangolila) die dunklen Werte bekommt; die vier hellen Themes überschreiben danach wieder auf hell. Schreibe die Blöcke so, dass das ohne `!important` und ohne Spezifitäts-Tricks aufgeht — im Zweifel die hellen Themes ihre Status-Werte **explizit** im eigenen Block setzen lassen, statt sich auf `:root` zu verlassen. Das ist ausdrücklich erlaubt und robuster; begründe deine Wahl im Report.

- [ ] **Step 4: Leisten-Rückfall, Marke und Skalen**

```scss
// ─── Leisten (Kopf-/Statuszeile) ──────────────────────────────────────────────
// Themes ohne eigene Werte erben hier: Kopfzeile auf der Seitenfläche,
// Statuszeile auf der Kartenfläche.
:root {
  --surface-header: var(--surface-page);
  --surface-statusbar: var(--surface-card);
  --text-bar: var(--text-primary);
  --text-bar-secondary: var(--text-secondary);
  --text-bar-muted: var(--text-muted);
```

**Hier ist der `var()`-Verweis richtig und beabsichtigt** — anders als bei den Paletten: Der Rückfall soll dem *jeweils geltenden* Theme folgen. Da `:root` und der aktive `[data-theme]`-Block am selben Element (`<html>`) hängen, löst sich `var(--surface-page)` gegen die Werte des aktiven Themes auf. Themes mit eigenen Leisten-Werten überschreiben schlicht.

`DEFAULT_THEME` wird zur Funktion:

```ts
/** Ohne eigene Wahl entscheidet die Systemeinstellung: dunkel → mangolila, hell → paper. */
function systemTheme(): ThemeKey {
  try {
    return window.matchMedia('(prefers-color-scheme: dark)').matches ? 'mangolila' : 'paper'
  } catch {
    return 'mangolila'
  }
}
```

`init()` nutzt sie als Rückfall. Der bestehende Whitelist-Check (`THEMES.some(...)`) trägt bereits, dass entfallene Namen sauber auf die Vorgabe fallen — das ist die Stelle, die deine Aufgabe schützt. **Keine** Umschreibung von `classic` (bewusste Entscheidung des Auftraggebers).
